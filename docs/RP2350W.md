# Single-chip DC-PicoLink on an RP2350 W (plan and status)

Goal: everything the RP2040-Zero + ESP32-S3 stack does today, on one Pico 2 W (RP2350 + CYW43 Wi-Fi).
Branch: `rp2350w/single-chip`. Nothing here has run on hardware.

## Dreamcast side: 4 signal pins (same as today)
The serial, SD and W5500 emulation all use the same Dreamcast lines, so the 4 pins carry everything:
GP9 CTS (+ clock sense), GP10 DC TXD, GP11 DC RXD, GP12 DC RTS, plus GP13 RTS -> 1 kΩ -> GP9 (flow control).
This is the existing `zero-stack` pin map (`DC_PIN_BASE=9`), so the plug wiring does not change.
Slot SD card: GP26 SCK, GP28 MISO, GP15 MOSI, GP14 CS (free on a Pico 2 W).

Pico 2 W conflicts: the CYW43 Wi-Fi chip owns GP23, GP24, GP25 and GP29. The power-sense wire (default GP29)
must move: build with `-DDC_POWER_PIN=<free GPIO>` (e.g. 22 or 27) and wire it there. The ESP32 link pins
(GP0-8) are no longer needed.

### Findings from the bring-up build (decide before going further)
- **Flash vs RAM:** the cable is built `copy_to_ram` (no flash-cache stalls on core 1). With Wi-Fi firmware
  and lwIP the image is 319 KB and cannot all sit in RAM next to 188 KB of data: the single-chip image runs from
  flash, so core 1's whole timing-critical call graph (`w5_header`, `w5_frames`, PIO servicing, SD) must be put in
  RAM function by function (`__not_in_flash_func`) and checked by disassembly.
- **NAT:** the ESP32's lwIP has NAPT (`lwip_napt.h`, used by ppp_srv.c to share the Wi-Fi with the Dreamcast).
  The Pico SDK's lwIP does not; it has to be ported (ESP-IDF's `ip4_napt.c` plus its hooks in `ip4.c`).
- **Core 0 is shared:** the cable's main loop (`main()` in main.c: USB, serial bridge, link) would become one
  FreeRTOS task next to lwIP and the network tasks; core 1 stays outside the RTOS.
- **ESP-IDF API layer:** esp32/main uses esp_timer, NVS, esp_http_server, OTA, esp_wifi, mDNS: each needs a
  Pico-side replacement; the `*_model.h` files and their tests carry over unchanged.

## What has to move from `esp32/main` (8300 lines, ESP-IDF specific) to the Pico SDK
Replace the SPI link between the chips with a direct in-memory call path (the `link_*` functions), keeping
the models (`*_model.h`) and their tests.

| Part | ESP-IDF today | On the RP2350 W |
|---|---|---|
| Wi-Fi, scan, saved networks | esp_wifi, NVS | cyw43_arch (STA), settings in flash |
| Network stack | lwIP + esp_netif | Pico SDK lwIP (NAT/forwarding, PPP server, DHCP/DNS need checking) |
| Web page, API, OTA | esp_http_server, OTA slots | own HTTP server on lwIP; update via UF2/page |
| PPP server, DNS, DCNow!, DCNet, Netlink, UPnP, mDNS | plain C on lwIP sockets | mostly portable once sockets are replaced |
| VPN (OpenVPN client, ~1100 lines) | mbedtls | mbedtls from the SDK; RAM is the question (520 KB shared with core1 timing code) |
| USB modem / cable on USB | USB host + CDC-ACM component | TinyUSB host on the native port or PIO-USB; then the USB port is no longer the flashing port |
| Cores | ESP32 two cores | core1 stays reserved for the cable timing path; Wi-Fi/lwIP on core0 |

Open risks: RAM (the debug build already runs from RAM and is near full on the RP2040), CPU time on core0 for
Wi-Fi + PPP + VPN at 250 MHz, and the CYW43 driver's interrupt latency near the cable's timing-critical code.

## Suggested order
1. RP2350 cable build verified on hardware (serial, SD, W5500 emulation) with the link replaced by a USB test host.
2. Wi-Fi + lwIP + PPP server + DNS: a serial game online (no VPN, no web page).
3. Web page, settings, update.
4. DCNow!, DCNet, Netlink, UPnP.
5. USB modem host.
6. VPN (last: biggest RAM and CPU cost).
